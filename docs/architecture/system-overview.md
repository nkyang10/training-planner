# System overview

One request path, one event path, one batch path. Keeping them separate is what makes the planner
deterministic and the UI fast.

## Components

### `packages/planner-core` — the brain, and the reason the rest exists
Pure TypeScript. `generate()` and `microAdjust()` per
[planner-engine.md](../engine/planner-engine.md). Zero dependencies beyond plain JS: no DB, no HTTP,
no LLM, no clock. Versioned independently; the deployed version and the knowledge hash are stamped on
every plan version so a 2026 plan can be regenerated byte-identically in 2028.

### `packages/domain` — contracts
Shared zod/JSON-Schema types: `AthleteProfile`, `PlanVersion`, `SessionSpec`, `DayEntry`,
`FactObject`, `SystemComment`, `ReviewRecord`, `PlanDiff`, plus the generated types from
`schemas/json/*`. One source of truth for web, api, worker, and eval.

### Policy evaluator
Loads the frozen knowledge bundle, evaluates rules in the documented precedence order against a
`SignalBundle`, emits typed `Action`s. Deterministic and pure too — it is the second component whose
output must be reproducible, because a review's justification depends on it.

### Narrator
Two paths, same output type:
- **Template path (default, always available):** rule id → template id → slot fill from `FactObject`
  → localised string. Deterministic, free, offline, auditable.
- **LLM path (optional enrichment):** structured-output call with the `FactObject` as the only source
  of facts; validated against `SystemComment` schema; guardrail-checked (every number must exist in
  the fact object; banned-topic blocklist; length and language checks; no diagnosis/promise/weight
  talk). On any failure, or LLM unavailable, or budget exhausted → fall back to the template path
  and record that it did.
The LLM is a *stylist*, never a *decider* ([AGENTS.md](../../AGENTS.md) rule 2). Cost envelope: a
comment per user per day is the entire LLM budget for v1; reviews add a narrative occasionally. The
fallback must be indistinguishable for the 80% of comments that are simple.

### Metrics service
Pure functions over the event log producing daily rollups (`load`, `CTL/ATL/TSB`, `wellnessEwma`,
`hrDrift`, `painTrajectory`). Recomputable from events at any time — this is why the log is
append-only and why a metric-definition fix can be back-filled. Each metric declares `requires[]`
(input set) so absent devices degrade visibly instead of silently.

### Integrations adapter
Pluggable `ActivitySource`: `manual` (always), `csv/gpx import`, `strava` (read-only), later others.
Normalises to `ActivityObserved` events with `provenance`. Identity resolution (which activity
belongs to which planned session) is its own module with an explicit `confidence` and a manual
"link this run to this day" fallback — a wrong auto-match corrupts adherence data and the comments
built on it, so ambiguity is surfaced, never guessed.

### Notifier
Timezone-aware, per-user preferences, and *low by design*: morning session card, evening feedback
nudge (one), review-ready notice. Reminder logic reads the same plan views the UI does; a nudge about
a session the safety layer already cancelled is a trust-ending bug, so notifications are generated
from the *current effective plan*, and suppressed when a `hard_stop` is open.

### Web app
Server-rendered calendar + island interactions; the day drawer is the whole product in one surface.
Offline entry capture via IndexedDB + background sync with idempotency keys. Full details:
[ux/screens.md](../ux/screens.md).

## Data flow: "evening entry" (the hot path, all of it)

1. `POST /entries` (idempotency key) → append `EntryLogged` + `DayEntry` row (single transaction).
2. Same transaction: upsert `metrics_rollups` for that user-day (cheap signals only).
3. Enqueue `evaluate-day` job (must be < 2 s end-to-end; the runner is still looking at the screen).
4. Worker: `computeSignals(user, upTo)` → `evaluatePolicies(signals, bundle)` → `actions[]`.
5. For a `comment` action: build `FactObject` → narrator → append `SystemComment` row + event.
6. For an `adjustTomorrow` action: `microAdjust()` (pure) → new `session_override` row + event
   (never a mutation of the plan version).
7. For a `flagReview` action: open/merge a `ReviewRecord` in `suggested` state, respecting
   [dwell/budget rules](../engine/review-trigger-policy.md#2-arbitration-when-several-triggers-fire).
8. UI reflects via a short-poll/SSE refresh of the day drawer.

**Failure posture:** steps 4–7 are re-runnable and idempotent. If the worker dies, the entry still
exists and the comment appears on retry. The runner's data is never lost to a commentary outage; and
if the LLM is down, comments still appear (template path).

## Batch paths
- Nightly: refine content horizon, recompute rollups, detect review triggers (cheap signals), send
  morning cards per user timezone.
- Weekly: regeneration + weekly summary + review-budget reset.
- Quarterly: aggregate (opt-in) pattern review → `knowledge/case-studies/`.

## Cross-cutting requirements

| Requirement | How |
|---|---|
| Determinism | pure core, injected clock/seed/knowledge hash, golden tests |
| Per-user isolation | Postgres RLS + `user_id` on every table + automated RLS test suite → [per-user-isolation.md](per-user-isolation.md) |
| Multi-language | message catalogues (`en`, `zh-Hant`), templated comments per locale, LLM instructed per locale and validated for script |
| Auditability | every plan version stores `{plannerVersion, knowledgeHash, inputsHash, ruleIds}`; every review stores `{evidenceSnapshotHash, options, chosen, reason}` |
| Portability | full season export (JSON + CSV + human-readable PDF/HTML), because the runner's history is the product's promise |
| Observability | per-user job traces, rule-fire counts, adjustment/revert counters, comment-fallback rate, review acceptance rate |
| Cost control | LLM behind a per-user per-day budget with cached template fallback; no LLM in any hot loop that computes a number |
